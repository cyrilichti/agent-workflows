---
title: /ready
description: Check completed work against its plan, then offer and perform promotion.
---

`/ready` has two entry paths: it receives the authoritative plan from `/work`,
or in standalone mode lets you select a recent plan. When the request ID is not
known, it asks for the exact pull-request number or merge-request IID.

## How this workflow is structured

<table className="workflow-steps">
  <tbody>
    <tr>
      <td>1</td>
      <th scope="row">Context</th>
      <td>Use caller context or select a completed plan.</td>
    </tr>
    <tr>
      <td>2</td>
      <th scope="row">Verify</th>
      <td>Require terminal work and one clean, non-behind branch snapshot.</td>
    </tr>
    <tr>
      <td>3</td>
      <th scope="row">Match</th>
      <td>Run only planned validation, then compare the complete branch diff with the Objective and Expected Outcome.</td>
    </tr>
    <tr>
      <td>4</td>
      <th scope="row">Confirm</th>
      <td>Show one concise promotion proposal and ask once.</td>
    </tr>
    <tr>
      <td>5</td>
      <th scope="row">Promote</th>
      <td>Push if needed, update and mark the request ready, attempt the item transition best-effort, and stop.</td>
    </tr>
  </tbody>
</table>
