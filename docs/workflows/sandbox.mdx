---
title: /sandbox
description: Prepare isolated worktrees and optional Docker services, then remove them by context.
---

`/sandbox` accepts a work item's ID, native URL, title, or search phrase and
prepares an isolated environment in the current project, returning a reusable JSON context.
Pass that context back to `/sandbox` to remove its resources. The workflow ends
after returning its result; delivery callers decide when to use the environment.

## What `/sandbox` does

<table className="workflow-steps">
  <tbody>
    <tr>
      <td>1</td>
      <th scope="row">Select</th>
      <td>A supplied <code>sandbox_context</code> selects teardown. For preparation, supply <code>item</code> as an ID, native URL, title, or search phrase. Resolve the official item and its plan in the current project. Stop if either cannot be resolved.</td>
    </tr>
    <tr>
      <td>2a</td>
      <th scope="row">Read the plan</th>
      <td>Preparation reads the authoritative plan. If it requires project code or services to run in a container, check for a Compose configuration, <a href="https://docs.docker.com/ai/sandboxes/get-started/">sbx</a>, Docker Engine, and Compose. If they are unavailable, create a worktree without container execution.</td>
    </tr>
    <tr>
      <td>3a</td>
      <th scope="row">Resolve dependencies</th>
      <td>Only for container execution, the agent identifies local repository dependencies from service and repository names in the README, then locates each with the existing project resolver command. It repeats this for the README of each located repository and supplies their absolute paths. Preparation validates those paths before allocation.</td>
    </tr>
    <tr>
      <td>4a</td>
      <th scope="row">Create</th>
      <td>Create a detached worktree at each selected repository's current <code>HEAD</code> and copy Git-ignored resources with their paths and permissions. When container execution is available, start Compose services in a uniquely named sbx shell sandbox and allocate ports. Return the resulting <code>sandbox_context</code>; on failure, attempt rollback and report the stage and reason.</td>
    </tr>
    <tr>
      <td>2b</td>
      <th scope="row">Tear down</th>
      <td>Verify context ownership, then remove its optional Docker sandbox and recorded worktrees. Accept partial preparation records and repeated teardown, preserve the main checkouts, and return the result.</td>
    </tr>
  </tbody>
</table>

Treat the resource root as private: its generated Compose file can contain
resolved environment values and is written with mode `0600`. The returned context
contains resource identities rather than secret values.

The command input, output, and failure contracts live at the call sites in
[`sandbox-prepare.md`](https://github.com/cyrilichti/agent-workflows/blob/main/workflows/sandbox-prepare.md)
and [`sandbox-teardown.md`](https://github.com/cyrilichti/agent-workflows/blob/main/workflows/sandbox-teardown.md).
