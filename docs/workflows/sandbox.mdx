title: /sandbox
description: Prepare isolated worktrees and optional Docker services, then remove them by context.

`/sandbox` prepares an isolated environment and returns a reusable JSON context.
Pass that context back to `/sandbox` to remove its resources. The workflow ends
after returning its result; delivery callers decide when to use the environment.

## What `/sandbox` does

<table className="workflow-steps">
  <tbody>
    <tr>
      <td>1</td>
      <th scope="row">Select</th>
      <td>A supplied <code>sandbox_context</code> selects teardown. Otherwise, preparation requires <code>item_id</code>, an absolute repository root in <code>project_directory</code>, and a boolean <code>browser_validation</code>.</td>
    </tr>
    <tr>
      <td>2</td>
      <th scope="row">Check</th>
      <td>Before allocation, preparation checks <a href="https://docs.docker.com/ai/sandboxes/get-started/">sbx</a> authentication and local startup diagnostics, Docker Engine, and Docker Compose. Browser validation requires a Compose configuration; when present, its variables, environment files, and file or environment secrets must resolve. External secrets, configs, networks, and volumes fail preflight because a fresh sandbox cannot resolve them.</td>
    </tr>
    <tr>
      <td>3</td>
      <th scope="row">Resolve</th>
      <td>Resolve README dependencies transitively through the shared project resolver, searching configured Codex projects and their neighbors. Recognize <code>Dependency:</code>, <code>Repository:</code>, and <code>Repo:</code> lines and relative Markdown links outside the repository. Compose build contexts, Dockerfiles, bind sources, environment files, secrets, and configs identify repositories by path. Missing or ambiguous dependencies stop preparation.</td>
    </tr>
    <tr>
      <td>4</td>
      <th scope="row">Prepare</th>
      <td>Create a detached worktree at each resolved repository's current <code>HEAD</code> and copy Git-ignored resources with their paths and permissions. For browser validation, start Compose services in a uniquely named sbx shell sandbox and allocate a separate sandbox port and an available host port on loopback for each published service port.</td>
    </tr>
    <tr>
      <td>5</td>
      <th scope="row">Tear down</th>
      <td>Verify context ownership, then remove its optional Docker sandbox and recorded worktrees. Accept partial preparation records and repeated teardown; preserve the main checkouts.</td>
    </tr>
    <tr>
      <td>6</td>
      <th scope="row">Return</th>
      <td>Return the command's JSON result unchanged. Preparation returns repository paths, ports, and the optional Docker sandbox in a reusable context. Failure reports its stage and reason; preparation attempts rollback and returns any allocated context. Keep that context for cleanup retry.</td>
    </tr>
  </tbody>
</table>

Treat the resource root as private: its generated Compose file can contain
resolved environment values and is written with mode `0600`. The returned context
contains resource identities rather than secret values.

The command input, output, and failure contracts live at the call sites in
[`workflows/sandbox.md`](https://github.com/cyrilichti/agent-workflows/blob/main/workflows/sandbox.md).
