title: /plan
description: Turn one task into a clear, approved implementation plan before work begins.
---

`/plan` turns a task into an implementation plan before work begins.
It first checks that the task can be delivered as one coherent unit. If the
task is too broad, standalone mode reports why and stops; caller mode returns
the findings so the caller can offer `/refine`.

## How this workflow is structured

<table class="workflow-steps">
  <tbody>
    <tr>
      <td>1</td>
      <th scope="row">Context</th>
      <td>Use standalone conversation context or preserve the official item supplied by a caller.</td>
    </tr>
    <tr>
      <td>2</td>
      <th scope="row">Scope</th>
      <td>Check that the task can be delivered as one coherent unit.</td>
    </tr>
    <tr>
      <td>3</td>
      <th scope="row">Specialist</th>
      <td>Select the right specialist to inspect the technical context and author the plan.</td>
    </tr>
    <tr>
      <td>4</td>
      <th scope="row">Plan</th>
      <td>Structure the work, verify external facts when needed, and challenge high-risk decisions.</td>
    </tr>
    <tr>
      <td>5</td>
      <th scope="row">Review</th>
      <td>Show only the plan name, link, and todo count, then approve or adjust it.</td>
    </tr>
    <tr>
      <td>6</td>
      <th scope="row">Return</th>
      <td>Return the approved plan or refinement findings to the caller; standalone mode stops.</td>
    </tr>
  </tbody>
</table>
