`/work` turns an approved plan into confirmed commits. It can receive the plan
from `/pick` with an active official item, or let you select from recent plans.
After completing the todos, it lets you stop or continue with `/ready` using
the same plan, optional item, and known request ID. `/ready` owns global
validation and push confirmation.

## How this workflow is structured

<table className="workflow-steps">
  <tbody>
    <tr>
      <td>1</td>
      <th scope="row">Plan</th>
      <td>Use the supplied plan or select one in standalone mode.</td>
    </tr>
    <tr>
      <td>2</td>
      <th scope="row">Branch</th>
      <td>Initialize new work or trust the current branch when resuming.</td>
    </tr>
    <tr>
      <td>3</td>
      <th scope="row">Request</th>
      <td>Create the draft pull request or merge request for new work.</td>
    </tr>
    <tr>
      <td>4</td>
      <th scope="row">Agent</th>
      <td>Select the most suitable agent, then reuse it while its cohort remains appropriate.</td>
    </tr>
    <tr>
      <td>5</td>
      <th scope="row">Todo</th>
      <td>Persist the todo as in progress, implement and validate it, then stage only its changes.</td>
    </tr>
    <tr>
      <td>6</td>
      <th scope="row">Commit</th>
      <td>Confirm the proposal, create the commit, then persist the todo as completed and continue.</td>
    </tr>
    <tr>
      <td>7</td>
      <th scope="row">Ready</th>
      <td>When work is completed, choose whether to stop or continue with <code>/ready</code>.</td>
    </tr>
  </tbody>
</table>

`/work` never pushes todo commits. `/ready` performs global validation and owns
the final push and request promotion. When resumed work no longer has its
initialized request record in context, `/ready` asks for the exact pull-request
number or merge-request IID.
