---
title: /project
description: Resolve a ticket destination to one local project directory.
---

`/project` locates the local Git repository for a work item when you have its
destination name (`list`) and exact ID. It returns one absolute project path or
an unresolved status.

## What `/project` does

<table class="workflow-steps">
  <tbody>
    <tr>
      <td>1</td>
      <th scope="row">Require</th>
      <td>Reject a missing or blank <code>list</code> or exact item ID before searching.</td>
    </tr>
    <tr>
      <td>2</td>
      <th scope="row">Search</th>
      <td>Search configured project directories first, then repositories directly inside their parent directories. Prefer the longest full repository name contained in the normalized destination; use repository family prefixes only when no full name matches.</td>
    </tr>
    <tr>
      <td>3</td>
      <th scope="row">Choose</th>
      <td>For several matches, use an explicit repository reference or one unique name mention in the complete item, then apply stable tie breaks if neither distinguishes candidates.</td>
    </tr>
    <tr>
      <td>4</td>
      <th scope="row">Return</th>
      <td>Return one absolute path, <code>not found</code>, or <code>search incomplete</code>. Invalid input or a failed search is an error.</td>
    </tr>
  </tbody>
</table>

## Execution details

Invoke `/project` or `$project` with the destination name and item ID, or let
the Kestra `work` flow call it after `/next` returns an item. It reads the item
only when several repositories match the destination. Configured project paths
take priority when available; each selected search tier is completed so
competing matches can be resolved independently of discovery order.
